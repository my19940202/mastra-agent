# 家庭法律 Agent 学习阶段 1～9

这份文档记录本项目从 Prompt 驱动的法律预咨询 Agent，逐步演进为可测试、可恢复、可收集线索的工程系统。

当前进度：

- 阶段 1：结构化 Working Memory 与专业采集 Prompt ✅
- 阶段 2：案件充分度 Tool ✅
- 阶段 3：确定性 Workflow 路由 ✅
- 阶段 4：多轮状态与恢复 ✅（当前由 `ask_user` 承担交互挂起）
- 阶段 5：已完成第一版；阶段 6：已完成第一版；阶段 7～9：待完成

## 一、基础概念

### Agent

Agent 是使用大模型进行自然语言理解和决策的执行主体。

```text
Agent
├─ model：使用哪个大模型
├─ instructions：角色、规则和边界
├─ memory：对话历史与结构化状态
├─ tools：可以执行的确定性能力
└─ workflows：可以启动的多步骤流程
```

适合交给 Agent 的工作：

- 理解用户口语化、模糊或不完整的表达。
- 从一句话里提取多个案件事实。
- 判断用户是在咨询离婚、彩礼还是继承。
- 用温和、自然的方式确认事实或解释一般法律方向。

不适合只依靠 Agent 的工作：

- 强制执行固定业务步骤。
- 精确判断必填字段是否全部完成。
- 保存线索、扣款或修改数据库等重要操作。
- 要求每次运行都得到完全一致的结果。



### Working Memory

普通对话历史保存的是一串消息；Working Memory 保存的是当前任务的结构化状态。

用户说：

> 我们结婚三年，没有孩子，已经分居半年。

模型可以将其整理为：

```json
{
  "scenario": "divorce",
  "divorce": {
    "marriageDuration": "三年",
    "hasChildren": "没有",
    "separated": "是",
    "separationDuration": "半年"
  }
}
```

本项目使用 `scope: "thread"`，表示每个对话线程拥有独立案件状态，避免不同案件互相污染。

Working Memory 让 Agent 在当前会话中知道：

- 已经确认了什么。
- 哪些信息未知。
- 哪些说法存在争议。
- 用户拒绝回答什么。
- 下一步最值得询问什么。



### Schema

Schema 是数据结构约定。本项目使用 Zod 描述案件状态、Tool 输入输出和 Workflow 输入输出。

Schema 可以减少：

- 字段名称不统一。
- 模型随意改变输出格式。
- Tool 收到不合法参数。
- Workflow 上一步输出无法传给下一步。
- TypeScript 无法推断数据类型。

共享 Schema 位于 `src/mastra/legal-intake-schema.ts`。Agent、Tool 和 Workflow 共用同一个 Schema，可以降低数据结构逐渐不一致的风险。

## 二、Tool Calling



### Tool 的作用

大模型擅长理解和生成语言，但不擅长稳定执行确定性业务逻辑。Tool 把一段真实的 TypeScript 函数暴露给模型，让模型能够请求系统执行它。

适合做成 Tool 的工作：

- 调用外部 API。
- 查询数据库。
- 发送邮件或创建线索。
- 执行数学计算。
- 校验输入。
- 根据明确规则判断案件信息是否充分。

本项目的 `evaluate-case-readiness` Tool 根据结构化案件状态返回：

```json
{
  "decision": "needs_more_information",
  "recommendedStage": "basic_facts",
  "nextField": "divorce.marriageDuration",
  "nextQuestion": "你们登记结婚大约多久了？",
  "missingCriticalFacts": [],
  "reason": "仍缺少会影响处理方向的关键信息。"
}
```



### 大模型调用 Tool 时具体发生什么

Agent 调用大模型时，Mastra 不只发送用户消息，还会发送可用 Tool 的名称、描述和输入 Schema。

```text
用户消息
  ↓
Mastra 将消息、instructions、memory、Tool Schema 发给模型
  ↓
模型选择下一步
  ├─ 输出普通文本
  └─ 输出 Tool Call
       ↓
Mastra 校验 Tool 参数
       ↓
执行 Tool 的 execute(inputData, context)
       ↓
将 Tool Result 加回模型上下文
       ↓
模型继续调用其他 Tool，或者生成最终回复
```

模型生成的 Tool Call 可以理解为：

```json
{
  "name": "evaluateCaseReadiness",
  "arguments": {
    "caseState": {
      "scenario": "divorce",
      "userGoal": "想离婚"
    }
  }
}
```

模型不会直接执行 TypeScript。Mastra 收到这个结构后，才会找到对应 Tool、校验输入并调用 `execute`。

### 谁决定是否调用 Tool

仅把 Tool 放进 Agent：

```ts
tools: {
  evaluateCaseReadiness: evaluateCaseReadinessTool,
}
```

只代表 Tool 对模型可用，不代表模型必定调用。

默认 `toolChoice` 相当于 `auto`：

- `auto`：模型决定是否调用。
- `none`：禁止调用 Tool。
- `required`：至少调用一个 Tool。
- `{ type: "tool", toolName: "..." }`：要求调用指定 Tool。

模型会综合用户消息、instructions、Tool description、inputSchema、历史消息和 Working Memory 作出选择。因此，Prompt 中写“必须调用 Tool”仍属于对模型的自然语言要求，不是绝对程序控制。

### Tool Calling 的工程价值

把案件充分度从 Prompt 移到 Tool，不是为了让 Agent 多问几轮，而是为了获得：

- 确定性：相同结构化输入得到相同判断。
- 可测试：不调用大模型也能测试业务规则。
- 可解释：能够看到缺失字段、下一字段和判断原因。
- 可复用：Agent、表单、Workflow 和 CRM 可以复用同一函数。
- 可维护：律师调整采集标准时修改代码，不必反复改长 Prompt。
- 可审计：能够在 Trace 中看到 Tool 的输入和输出。

Tool 仍依赖模型正确提取事实。如果模型把用户没有说过的内容写入 `caseState`，Tool 会基于错误输入得到稳定但错误的结果。

## 三、Workflow 与 Tool 的区别

一句话区别：

```text
Tool 解决“执行一个能力”。
Workflow 解决“按什么顺序执行多个步骤”。
```


| 对比项       | Tool              | Workflow                     |
| --------- | ----------------- | ---------------------------- |
| 主要职责      | 完成一个清晰动作          | 编排多个步骤和分支                    |
| 典型结构      | 输入 → execute → 输出 | step → branch → step → 输出    |
| 是否适合业务流程  | 只适合其中一个动作         | 适合完整业务过程                     |
| 谁决定是否调用   | 默认由模型决定，也可由代码调用   | 可由模型启动，也可由应用代码启动             |
| 状态        | 通常一次执行完成          | 可以维护 Workflow state          |
| 暂停恢复      | 可以支持挂起，但不擅长表达完整流程 | 原生支持 `suspend/resume` 和持久化快照 |
| 分支与循环     | 通常写在函数内部          | 提供 `.branch()`、循环和并行控制流      |
| Studio 展示 | 查看一次 Tool 输入输出    | 查看 Graph、步骤状态和实际路径           |
| 本项目示例     | 判断案件信息是否充分        | 采集、挂起、恢复并路由回复模式              |




### 本项目中的演进关系

阶段 2 只有 Tool：

```text
Agent
  → 模型决定调用 evaluateCaseReadiness
  → Tool 返回下一问题或 ready
  → Agent 回复
```

阶段 3 加入 Workflow：

```text
Workflow
  → 执行充分度判断
  → branch
      ├─ ask_question
      ├─ provide_guidance
      ├─ create_handoff
      ├─ handle_safety
      └─ decline_out_of_scope
  → 输出统一 responsePlan
```

阶段 4 最初使用 Workflow 自身的 `suspend/resume` 探索多轮恢复。当前实现调整为“每轮重新评估完整案件状态”，并由 Agent 的 `ask_user` Tool 承担界面交互的挂起和恢复：

```text
Agent 收到用户事实
  → 更新 Working Memory
  → 启动一次 Workflow，评估完整 caseState
  → Workflow 返回 responsePlan
      ├─ 信息不足：Agent 调用 ask_user 并挂起
      └─ 信息充分：Agent 输出 guidance
  → 用户在卡片中回答，ask_user 恢复 Agent
  → 更新 Working Memory 并启动新一次 Workflow 评估
```

这样拆分以后，Workflow 只负责确定性地决定“下一步是什么”，`ask_user` 只负责“怎样在聊天界面收集这一个答案”。每次 Workflow Run 都可以独立在 Trace 中检查，不需要让模型拼装上一次 Workflow 的 resume 参数。

需要区分两层“是否强制”：

1. 应用或 Agent 是否启动 Workflow。
2. Workflow 启动后，内部是否按固定步骤执行。

从 Studio Workflows 页面或应用代码直接启动时，Workflow 内部流程不能跳过；从 Agent 对话入口启动时，是否发起 Workflow 仍可能受到模型 Tool Calling 决策影响。

- 创建 `legal-intake-workflow`。
- 根据 readiness 结果进入不同分支。

## 七、阶段 4：多轮状态与恢复 ✅

- 定义 Workflow state：`caseState`、`handoffRequested`、`turnCount` 和 `lastPlan`。
- Workflow 每轮根据完整 Working Memory 返回稳定的 `responsePlan`，不在 Workflow 内等待自然语言答案。
- Agent 使用 `ask_user` 挂起当前交互；用户提交卡片后恢复 Agent。
- 开启 `autoResumeSuspendedTools`，让 Studio 能继续执行被 `ask_user` 挂起的 Agent Run。
- 恢复后先更新 Working Memory，再启动一次新的 Workflow 评估。
-   阶段 3 = 确定性分支路由
    阶段 4 = 确定性分支路由
           + Workflow State
           + Working Memory
           + ask_user suspend/resume
           + Agent 对话自动恢复

仍需关注：自然语言回复如何可靠合并到 `caseState`，以及恢复后 Agent 是否确实重新运行 Workflow。

## 八、阶段 5：自动化评测与可观测性 ✅

目标是在收集真实线索前，证明 Agent 足够稳定。

本阶段已完成：

- 在 `src/mastra/evals/legal-intake-eval-cases.ts` 建立 10 个固定回归案例，作为可版本控制的测试题库，也可迁移到 Studio Dataset。
- 建立 4 个不调用 Judge 模型的确定性 Scorer：单轮最多一个问题、禁止绝对化法律结论、律师交接免责声明、安全优先响应。
- 把 Scorer 挂到 Agent，并在 `src/mastra/index.ts` 注册。每次 Agent 运行后会异步评分，评分不修改本轮回答。
- 在 `tests/legal-intake-scorers.test.ts` 增加规则级自动化测试，并提供 `pnpm test:legal-intake` 命令。
- 保留现有 Observability 与 Storage，便于在 Studio 的 Trace 中查看 Agent、Workflow、Tool 调用和评分结果。

当前自动评分覆盖：重复或合并提问、安全风险、绝对法律结论和律师摘要格式。固定案例还覆盖场景分类、未知或拒答、事实补写、过早 guidance 和范围外问题；这些行为仍需通过 Dataset Experiment 或人工 Trace 检查继续扩充为自动指标。

### Scorer、Trace 和 Dataset 分别解决什么问题

- **Scorer**：对一次实际输出按规则打分。例如回复出现两个问号则单问题规则为 0 分。
- **Trace**：记录这一次为什么得到该结果。可以看到 Agent 是否调用 Workflow、Workflow 进入哪个分支、`ask_user` 是否挂起或恢复，以及各节点耗时。
- **Dataset / 固定案例**：保存一批不会随手工测试变化的输入。改 Prompt、模型或代码后重新运行同一批题，才能比较是否发生退化。

它们的关系是：Dataset 提供固定题目，Agent 或 Workflow 产生输出，Scorer 给输出打分，Trace 帮助定位低分来自哪一个步骤。

### 怎样在本项目中测试

1. 运行 `pnpm test:legal-intake`，先验证确定性规则本身。
2. 运行 `pnpm dev`，在 Studio Agent 页面分别输入普通离婚问题、彩礼“能否全部返还”、紧迫家暴和“整理给律师”的案例。
3. 打开对应 Trace，确认能看到 `legal-intake-workflow` 调用与分支、`ask_user` 的挂起或恢复状态，以及 Scorer 分数和原因。
4. 修改 Prompt 或 Workflow 后，重复运行 `legalIntakeEvalCases` 中的固定输入，对比每项评分和 Trace。

注意：Scorer 是运行后的质量测量，不是执行前的拦截器。0 分会暴露问题，但不会自动撤回已经生成的回复；高风险场景若要做到强制阻断，需要在后续生产安全阶段增加输出校验与兜底逻辑。

完成标准：修改 Prompt、模型、Tool 或 Workflow 后，可以自动发现行为退化。

## 九、阶段 6：线索资格与用户授权 ✅

新增独立 Lead Schema，记录服务需求、紧迫程度、地区、材料情况、咨询意愿和资格状态。

```text
案件信息基本充分
→ 询问是否希望律师联系
→ 展示用途和授权范围
→ 用户明确同意
→ 才收集联系方式
```

案件事实、联系信息和授权记录应分开保存。

本阶段已完成：

- `legalLeadQualification`：只记录服务需求、地区、紧迫程度、材料情况、咨询意愿和资格状态。
- `legalLeadConsent`：独立记录授权状态、用途版本、授权范围和用户明确同意的原话。
- `legalLeadContact`：独立记录联系方式类型、联系方式值和偏好联系时间。
- `evaluate-legal-lead` Tool：确定性决定下一步是询问咨询意愿、请求明确授权、补充资格信息、收集联系方式，还是停止流程。
- 只有案件决定为 `ready_for_guidance` 或 `ready_for_handoff` 才具备线索资格。
- “愿意让律师联系”只代表有咨询意愿，不代表同意具体的数据用途和范围。
- 授权记录必须同时具备 `granted`、用途版本、完整授权范围和用户同意原话；仅有一个 `granted` 标记不能解锁联系方式采集。
- 用户拒绝或撤回后，Tool 强制返回 `mayCollectContact=false`。
- 阶段 6 不写数据库、不调用 CRM、不分配律师，也不声称已经建立委托关系。

### Studio 中的选择题和填空题

本项目使用 Mastra 内置的 `ask_user` Tool，而不是让 Agent 把所有问题输出成普通聊天文字。

```text
Workflow / Lead Tool
  → 返回 nextField、nextQuestion、questionPresentation
  → Agent 调用 ask_user
      ├─ text：显示文本输入框
      ├─ single_select：显示单选项
      └─ multi_select：显示多选项（结构已预留）
  → 用户提交
  → ask_user 恢复 Agent
  → 答案写入 Working Memory
```

题型由确定性字段映射决定：

- “是否共同生活”“是否有孩子”等封闭问题使用单选。
- “协议离婚还是诉讼离婚”“联系方式类型”等枚举问题使用单选。
- “结婚多久”“分居原因”“所在城市”等开放问题使用文本输入。
- 未配置的新字段默认使用文本输入，避免模型临时编造选项。

`ask_user` 的作用只是暂停、展示控件和返回答案。它不负责决定法律流程，也不会直接更新 Working Memory；这些仍由 Agent、Workflow 和确定性 Tool 分工完成。

### Reasoning 与业务回复

Reasoning 是模型或 Studio 展示的推理过程，不属于法律 Agent 的业务输出，也不能作为 Workflow 判断依据。本项目将模型的 `reasoning` 设置为 `none`，减少 Studio 中无须关注的推理内容；需要排查行为时应优先查看 Trace 中的 Tool 输入输出、Workflow 分支和 Working Memory，而不是依赖模型的自然语言推理。

### 阶段 6 的状态顺序

```text
案件尚未充分 / 安全优先 / 范围外
→ not_eligible（不得采集联系方式）

案件基本充分
→ awaiting_interest
→ awaiting_consent
→ collecting_details（地区、紧迫程度、材料情况）
→ 联系方式类型
→ 联系方式值
→ qualified
```

### 怎样测试

1. 在 Studio 的 Tools 页面单独运行 `evaluate-legal-lead`，验证同一份 leadState 在不同授权状态下的输出。
2. 当 `consent.status` 缺失、为 `declined`、为 `withdrawn`，或只有 `granted` 而缺少完整授权记录时，确认 `mayCollectContact=false`。
3. 在 Agent 新对话中先完成案件采集，再回答“希望律师联系”，确认下一步是授权说明而不是索取手机号。
4. 使用虚构联系方式测试；正式处理真实联系方式前仍需完成阶段 7 和阶段 9。
5. 运行 `pnpm test:legal-intake`，检查资格顺序、拒绝和撤回等确定性约束。

- 限流、异常处理和人工兜底。
- 隐私与授权文本的专业审核。
- 部署、监控和告警。



## 十三、后续推进顺序

```text
阶段 7：保存及律师交接
→ 阶段 8：RAG
→ 阶段 9：生产上线
```

- 阶段 4～7 是实现可靠线索收集的主线。
- 阶段 8 用于提升法律回答质量，不是线索 MVP 的前置条件。
- 阶段 9 是接触真实用户和真实联系方式前的必要条件。

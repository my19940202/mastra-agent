# 家庭法律 Agent 学习阶段 1～9

这份文档记录本项目从 Prompt 驱动的法律预咨询 Agent，逐步演进为可测试、可恢复、可收集线索的工程系统。

当前进度：

- 阶段 1：结构化 Working Memory 与专业采集 Prompt ✅
- 阶段 2：案件充分度 Tool ✅
- 阶段 3：确定性 Workflow 路由 ✅
- 阶段 4：多轮 Workflow `suspend/resume` ✅
- 阶段 5～9：待完成

## 一、基础概念

### Agent

Agent 是使用大模型进行自然语言理解和决策的执行主体。

```text
Agent
├─ model：使用哪个大模型
├─ instructions：角色、规则和边界
├─ memory：对话历史与结构化状态
├─ tools：可以执行的确定性能力
└─ workflows：可以启动的多步骤流程
```

适合交给 Agent 的工作：

- 理解用户口语化、模糊或不完整的表达。
- 从一句话里提取多个案件事实。
- 判断用户是在咨询离婚、彩礼还是继承。
- 用温和、自然的方式确认事实或解释一般法律方向。

不适合只依靠 Agent 的工作：

- 强制执行固定业务步骤。
- 精确判断必填字段是否全部完成。
- 保存线索、扣款或修改数据库等重要操作。
- 要求每次运行都得到完全一致的结果。



### Working Memory

普通对话历史保存的是一串消息；Working Memory 保存的是当前任务的结构化状态。

用户说：

> 我们结婚三年，没有孩子，已经分居半年。

模型可以将其整理为：

```json
{
  "scenario": "divorce",
  "divorce": {
    "marriageDuration": "三年",
    "hasChildren": "没有",
    "separated": "是",
    "separationDuration": "半年"
  }
}
```

本项目使用 `scope: "thread"`，表示每个对话线程拥有独立案件状态，避免不同案件互相污染。

Working Memory 让 Agent 在当前会话中知道：

- 已经确认了什么。
- 哪些信息未知。
- 哪些说法存在争议。
- 用户拒绝回答什么。
- 下一步最值得询问什么。



### Schema

Schema 是数据结构约定。本项目使用 Zod 描述案件状态、Tool 输入输出和 Workflow 输入输出。

Schema 可以减少：

- 字段名称不统一。
- 模型随意改变输出格式。
- Tool 收到不合法参数。
- Workflow 上一步输出无法传给下一步。
- TypeScript 无法推断数据类型。

共享 Schema 位于 `src/mastra/legal-intake-schema.ts`。Agent、Tool 和 Workflow 共用同一个 Schema，可以降低数据结构逐渐不一致的风险。

## 二、Tool Calling



### Tool 的作用

大模型擅长理解和生成语言，但不擅长稳定执行确定性业务逻辑。Tool 把一段真实的 TypeScript 函数暴露给模型，让模型能够请求系统执行它。

适合做成 Tool 的工作：

- 调用外部 API。
- 查询数据库。
- 发送邮件或创建线索。
- 执行数学计算。
- 校验输入。
- 根据明确规则判断案件信息是否充分。

本项目的 `evaluate-case-readiness` Tool 根据结构化案件状态返回：

```json
{
  "decision": "needs_more_information",
  "recommendedStage": "basic_facts",
  "nextField": "divorce.marriageDuration",
  "nextQuestion": "你们登记结婚大约多久了？",
  "missingCriticalFacts": [],
  "reason": "仍缺少会影响处理方向的关键信息。"
}
```



### 大模型调用 Tool 时具体发生什么

Agent 调用大模型时，Mastra 不只发送用户消息，还会发送可用 Tool 的名称、描述和输入 Schema。

```text
用户消息
  ↓
Mastra 将消息、instructions、memory、Tool Schema 发给模型
  ↓
模型选择下一步
  ├─ 输出普通文本
  └─ 输出 Tool Call
       ↓
Mastra 校验 Tool 参数
       ↓
执行 Tool 的 execute(inputData, context)
       ↓
将 Tool Result 加回模型上下文
       ↓
模型继续调用其他 Tool，或者生成最终回复
```

模型生成的 Tool Call 可以理解为：

```json
{
  "name": "evaluateCaseReadiness",
  "arguments": {
    "caseState": {
      "scenario": "divorce",
      "userGoal": "想离婚"
    }
  }
}
```

模型不会直接执行 TypeScript。Mastra 收到这个结构后，才会找到对应 Tool、校验输入并调用 `execute`。

### 谁决定是否调用 Tool

仅把 Tool 放进 Agent：

```ts
tools: {
  evaluateCaseReadiness: evaluateCaseReadinessTool,
}
```

只代表 Tool 对模型可用，不代表模型必定调用。

默认 `toolChoice` 相当于 `auto`：

- `auto`：模型决定是否调用。
- `none`：禁止调用 Tool。
- `required`：至少调用一个 Tool。
- `{ type: "tool", toolName: "..." }`：要求调用指定 Tool。

模型会综合用户消息、instructions、Tool description、inputSchema、历史消息和 Working Memory 作出选择。因此，Prompt 中写“必须调用 Tool”仍属于对模型的自然语言要求，不是绝对程序控制。

### Tool Calling 的工程价值

把案件充分度从 Prompt 移到 Tool，不是为了让 Agent 多问几轮，而是为了获得：

- 确定性：相同结构化输入得到相同判断。
- 可测试：不调用大模型也能测试业务规则。
- 可解释：能够看到缺失字段、下一字段和判断原因。
- 可复用：Agent、表单、Workflow 和 CRM 可以复用同一函数。
- 可维护：律师调整采集标准时修改代码，不必反复改长 Prompt。
- 可审计：能够在 Trace 中看到 Tool 的输入和输出。

Tool 仍依赖模型正确提取事实。如果模型把用户没有说过的内容写入 `caseState`，Tool 会基于错误输入得到稳定但错误的结果。

## 三、Workflow 与 Tool 的区别

一句话区别：

```text
Tool 解决“执行一个能力”。
Workflow 解决“按什么顺序执行多个步骤”。
```


| 对比项       | Tool              | Workflow                     |
| --------- | ----------------- | ---------------------------- |
| 主要职责      | 完成一个清晰动作          | 编排多个步骤和分支                    |
| 典型结构      | 输入 → execute → 输出 | step → branch → step → 输出    |
| 是否适合业务流程  | 只适合其中一个动作         | 适合完整业务过程                     |
| 谁决定是否调用   | 默认由模型决定，也可由代码调用   | 可由模型启动，也可由应用代码启动             |
| 状态        | 通常一次执行完成          | 可以维护 Workflow state          |
| 暂停恢复      | 可以支持挂起，但不擅长表达完整流程 | 原生支持 `suspend/resume` 和持久化快照 |
| 分支与循环     | 通常写在函数内部          | 提供 `.branch()`、循环和并行控制流      |
| Studio 展示 | 查看一次 Tool 输入输出    | 查看 Graph、步骤状态和实际路径           |
| 本项目示例     | 判断案件信息是否充分        | 采集、挂起、恢复并路由回复模式              |




### 本项目中的演进关系

阶段 2 只有 Tool：

```text
Agent
  → 模型决定调用 evaluateCaseReadiness
  → Tool 返回下一问题或 ready
  → Agent 回复
```

阶段 3 加入 Workflow：

```text
Workflow
  → 执行充分度判断
  → branch
      ├─ ask_question
      ├─ provide_guidance
      ├─ create_handoff
      ├─ handle_safety
      └─ decline_out_of_scope
  → 输出统一 responsePlan
```

阶段 4 支持多轮：

```text
Workflow Run
  → 评估 caseState
  → 信息不足
  → suspend(nextQuestion)
  → 用户回答
  → resume(完整的新 caseState)
  → 再次评估
  → 信息充分
  → guidance
  → success
```

需要区分两层“是否强制”：

1. 应用或 Agent 是否启动 Workflow。
2. Workflow 启动后，内部是否按固定步骤执行。

从 Studio Workflows 页面或应用代码直接启动时，Workflow 内部流程不能跳过；从 Agent 对话入口启动时，是否发起 Workflow 仍可能受到模型 Tool Calling 决策影响。

## 四、阶段 1：结构化记忆与采集 Prompt ✅

- 建立离婚、彩礼、继承与家庭财产场景。
- 使用 Zod 定义结构化案件字段。
- 使用 thread Working Memory 隔离案件。
- 定义安全优先、单轮单问题、未知、争议和拒答规则。
- 将律师手册中的彩礼采集经验转换为中立字段。
- 避免把典型案例直接套用为用户案件结论。

这一阶段学习的是：怎样让大模型成为一个有角色、边界和上下文的 Agent。

## 五、阶段 2：案件充分度 Tool ✅

- 建立 `evaluateCaseReadiness` 确定性函数。
- 创建 `evaluate-case-readiness` Tool。
- 为离婚、彩礼和继承定义最低必要事实。
- 返回单一下一字段和下一问题。
- 增加安全优先、主动 handoff 和范围外判断。
- 为 Tool 编写不依赖模型的确定性测试。

这一阶段学习的是：怎样把业务判断从 Prompt 迁移到可测试代码。

## 六、阶段 3：确定性 Workflow 路由 ✅

- 创建 `legal-intake-workflow`。
- 根据 readiness 结果进入不同分支。
- 将分支结果统一为 `responsePlan`。
- 注册 Workflow，并让 Agent 可以启动它。
- 在 Studio Graph 和 Trace 中观察执行路径。

这一阶段学习的是：Tool 是能力，Workflow 是对能力的编排。

## 七、阶段 4：多轮 Workflow ✅

- 定义 Workflow state：`caseState`、`handoffRequested`、`turnCount` 和 `lastPlan`。
- 信息不足时调用 `suspend()`。
- 使用 `resumeSchema` 接收更新后的完整案件状态。
- 在同一个 Workflow Run 中多次挂起和恢复。
- 开启 `autoResumeSuspendedTools`，允许同一 Agent 线程的下一条消息自动恢复。
- 验证 `suspended → suspended → success` 的完整过程。
-   阶段 3 = 确定性分支路由
    阶段 4 = 确定性分支路由
           + Workflow State
           + suspend/resume
           + 持久化快照
           + 对话自动恢复

仍需关注：自然语言回复如何可靠合并到 `caseState`，以及 Agent 是否始终启动同一个 Workflow Run。

## 八、阶段 5：自动化评测与可观测性

目标是在收集真实线索前，证明 Agent 足够稳定。

计划增加：

- 固定测试案例 Dataset。
- Scorers。
- Workflow/Agent Trace 检查。
- CI 中的确定性测试。

重点评测：场景分类、重复提问、事实补写、安全风险、过早 guidance、绝对法律结论和律师摘要质量。

完成标准：修改 Prompt、模型、Tool 或 Workflow 后，可以自动发现行为退化。

## 九、阶段 6：线索资格与用户授权

新增独立 Lead Schema，记录服务需求、紧迫程度、地区、材料情况、咨询意愿和资格状态。

```text
案件信息基本充分
→ 询问是否希望律师联系
→ 展示用途和授权范围
→ 用户明确同意
→ 才收集联系方式
```

案件事实、联系信息和授权记录应分开保存。

## 十、阶段 7：线索保存与律师交接

实现 `createLegalLead` Tool，并接入数据库或 CRM。

```text
readiness 通过
AND 用户希望律师联系
AND 已明确授权
AND 联系方式校验通过
```

需要覆盖幂等性、状态流转、人工审核、律师分配、失败重试和审计日志。

## 十一、阶段 8：法律知识库与 RAG

在案件采集稳定后，再接入现行法律法规、司法解释、最高法公开案例、地方办理指南和律师审核后的业务手册。

每份知识应记录来源、效力、适用地区、发布日期、审核时间和版本。律师手册应先校验和拆分，不直接把全文塞进 Prompt。

## 十二、阶段 9：生产安全与上线

正式收集真实线索前完成：

- 身份认证与权限控制。
- 敏感字段加密和日志脱敏。
- 数据访问审计、保存期限和删除机制。
- 用户撤回授权。
- Prompt 注入防护。
- 限流、异常处理和人工兜底。
- 隐私与授权文本的专业审核。
- 部署、监控和告警。



## 十三、后续推进顺序

```text
阶段 5：评测与可观测性
→ 阶段 6：线索资格与授权
→ 阶段 7：保存及律师交接
→ 阶段 8：RAG

```
